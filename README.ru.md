# GitHub Pixel Diff

**Русский** · [English](README.md)

[**Поставить из Chrome Web Store**][store] ·
[**Сравнить две картинки прямо сейчас, ничего не устанавливая**][site] ·
[Firefox Add-ons][amo] (на проверке)

GitHub и GitLab умеют показывать две версии картинки рядом, шторкой и
наложением, но не умеют главного: сказать, **что именно** изменилось. На снимке
страницы высотой в три тысячи пикселей правка занимает четыре строки — и найти
их глазами нельзя.

Расширение добавляет к режимам **2-up**, **Swipe** и **Onion Skin** четвёртый —
**Pixel Diff**: он считает разницу попиксельно и сразу показывает тот фрагмент,
где она уместилась. Работает и в просмотрщике GitHub, и в мердж-реквестах на
`gitlab.com`.

![Режим Pixel Diff](docs/screenshots/frame-changes.png)

**Нет под рукой пул-реквеста?** То же сравнение работает и на своих файлах:
<https://nemo-illusionist.github.io/gh-pixel-diff/> — положите туда две картинки
и получите ту же разницу. Никуда ничего не загружается: страница статическая, а
сравнение идёт в браузере.

## Что умеет

- Встаёт четвёртой кнопкой в родной ряд режимов — отдельной панели нет.
- Открывается на фрагменте с изменениями; кадр целиком — по ссылке в подписи,
  с красной рамкой вокруг изменившегося места; рамку можно убрать, и выбор
  запомнится.
- Считает, сколько пикселей изменилось и какую долю кадра это составляет.
- Ползунок порога — от «ловить даже сглаживание» до «только заметное глазу»,
  в том же виде, что и ползунок Onion Skin.
- Переключатель «до / после / разница / **3-up**» под кадром: любая из версий
  поодиночке или все три рядом — всегда в том же масштабе и той же обрезке, что
  и разница, чего родные 2-up и Swipe не умеют. Выбор запоминается, а сам
  переключатель выключается на странице настроек.
- Разные размеры «до» и «после» не ломают сравнение: кадры выравниваются по
  левому верхнему углу, а изменение размера попадает в подпись.
- Работает в приватных репозиториях: адреса картинок берутся из фрейма, который
  GitHub уже собрал, — вместе с подписью в ссылке, — а не составляются заново по
  имени репозитория.
- Если пул-реквест пришёл из форка, а форк потом удалили, картинка берётся из
  основного репозитория — GitHub в этом случае показывает «Invalid image source».
- Выбранный режим переносится на следующую картинку пул-реквеста — не нужно
  нажимать Pixel Diff в каждом из двадцати файлов.
- SVG растрируется в разумном размере, а не в 300×150, которые браузер выдумывает
  вектору без собственного размера; в подписи сказано, в чём считали.
- Сравнение идёт в отдельном потоке: панель не подвисает на снимках в несколько
  мегапикселей, и картинки хранятся там же, а не в памяти фрейма.
- Интерфейс английский, а при русском языке браузера — русский.

## Установка

**Chrome, Edge, любой Chromium** — [в Chrome Web Store][store]. Одна кнопка,
и обновления приходят сами.

Всё, что ниже, — для остальных браузеров и для тех, кто предпочитает ставить
свою сборку. Готовые архивы — на странице
[релизов](https://github.com/Nemo-Illusionist/gh-pixel-diff/releases). Их
собирает GitHub из этого же репозитория; суммы SHA-256 лежат рядом в
`checksums.txt`. Из исходников — `npm run build`, дальше те же шаги, только
вместо распакованного архива берётся папка `dist/`.

### Chrome, Edge, любой Chromium — из архива

1. Скачать и распаковать `gh-pixel-diff-chrome-*.zip`.
2. Открыть `chrome://extensions` и включить «Режим разработчика».
3. «Загрузить распакованное расширение» → распакованная папка.

### Firefox

Дополнение отправлено на [addons.mozilla.org][amo] и ждёт проверки — пока она
не прошла, страница не открывается, и остаётся архив:

1. Скачать `gh-pixel-diff-firefox-*.zip` (распаковывать не нужно).
2. Открыть `about:debugging#/runtime/this-firefox`.
3. «Загрузить временное дополнение» → выбрать архив.

Временное дополнение живёт до перезапуска браузера: постоянное Firefox поставит
только подписанное, а подписью проверка как раз и заканчивается.

### Safari, macOS

Safari не ставит расширения из папки: нужен проект Xcode, приложение-контейнер
и подпись. Без сертификата macOS расширение попросту не зарегистрирует, и в
списке Safari оно не появится — бесплатного Apple ID, добавленного в Xcode
(Settings → Accounts), для этого достаточно.

1. Скачать и распаковать `gh-pixel-diff-safari-*.zip`, дальше — по
   `SAFARI-INSTALL.txt` внутри. Из исходников то же делает
   `npm run build:safari` (при первом запуске конвертер может потребовать
   `sudo xcodebuild -runFirstLaunch`).
2. Открыть полученный проект, в настройках цели выбрать свою команду
   разработчика.
3. Собрать схему «GitHub Pixel Diff (macOS)» и запустить приложение-контейнер.
4. Safari → Настройки → Расширения → включить расширение.
5. Нажать кнопку расширения в панели Safari и выбрать «Разрешить доступ».

Из исходников всё это делает `npm run install:macos`: собирает, подписывает
первым найденным сертификатом разработчика, ставит приложение в `/Applications`
и снимает с учёта временную копию из папки сборки — иначе Safari показывает
расширение дважды.

Последний шаг — не формальность. Safari не распространяет разрешение для сайта
на кросс-доменные фреймы, а картинки живут именно во фрейме, поэтому доступ
нужен к `viewscreen.githubusercontent.com` — домену, который в адресной строке
никто не открывает.

### Safari, iPhone и iPad

Тот же проект, схема с суффиксом `(iOS)`, сборка на своё устройство из Xcode —
других способов нет: расширения в мобильный Safari попадают либо так, либо из
App Store.

1. Поставить платформу iOS (Xcode → Настройки → Компоненты, либо
   `xcodebuild -downloadPlatform iOS`).
2. Выбрать схему «GitHub Pixel Diff (iOS)» и своё устройство, собрать.
3. Настройки → Приложения → Safari → Расширения → включить.

Бесплатный аккаунт разработчика даёт сертификат на семь дней, после чего проект
нужно пересобрать. Постоянная установка — только через App Store, а для неё
нужен платный Apple Developer Program.

### Android

Chrome на Android расширения не поддерживает — ни это, ни любое другое.
Остаётся Firefox, но временные дополнения там недоступны: нужна подписанная
сборка.

## Выдача доступа

Как бы расширение ни было установлено, ему нужен доступ к двум доменам:
`viewscreen.githubusercontent.com` — фрейм, в котором GitHub рисует картинки, —
и `gitlab.com`, где GitLab рисует их прямо на странице. Chrome и Firefox выдают
доступ при установке, Safari — нет: разрешение для сайта там не распространяется
на кросс-доменные фреймы, а картинки GitHub живут именно во фрейме.

Доступ запрашивается из окна самого расширения: нажмите его кнопку в панели
браузера и в окне — **Разрешить доступ**. Ничего другого в окне нет: состояние
доступа и строка ссылок, всё остальное — на странице настроек.

![Окно расширения](docs/screenshots/popup.png)

Страница настроек открывается из того же окна, ссылкой **Настройки**, а в Safari
— из Настройки → Расширения → GitHub Pixel Diff → **Настройки**. Там же рядом —
родная кнопка Safari «Изменить сайты…», которая выдаёт доступ без всякого окна:
поставить `viewscreen.githubusercontent.com` в «Разрешить».

Больше заранее не запрашивается ничего. Прав на страницы `github.com` нет вовсе,
так что ни ваших репозиториев, ни сессии расширение не видит. Ничего не
собирается и никуда не отправляется —
[политика конфиденциальности](docs/PRIVACY.md).

### Свой сервер GitLab

Свой GitLab живёт по адресу, которого манифест знать заранее не может, —
попросить такой доступ при установке нельзя. Поэтому адрес добавляется руками, на странице
настроек: вписать хост — `gitlab.example.com` — и нажать **Добавить**. Браузер
спросит про доступ к этому одному адресу; после согласия расширение регистрирует
на нём свой скрипт, и режим появляется в просмотрщике картинок этого сервера.
Если сервер уже открыт, вкладку нужно перезагрузить.

Список на той же странице показывает выданные адреса, а **Убрать** снимает и
разрешение, и регистрацию. Список этот не наш: он читается у браузера при каждом
открытии страницы, поэтому разрешение, отозванное в настройках самого браузера,
из него тоже исчезает.

На странице, которая не GitLab, расширение не делает ничего — какой бы адрес ни
был выдан: прежде чем трогать разметку, оно ищет родную пометку GitLab
`data-page`.

## Что проверено

| Цель | Состояние |
|---|---|
| Chrome / Chromium | Проверено на живой странице пул-реквеста, тест в наборе |
| Firefox | Сборка проходит проверку `web-ext lint` без замечаний; в браузере не гонялась |
| Safari, macOS | Схема компилируется; включение расширения в браузере — вручную |
| Safari, iOS | Схема компилируется, контейнер ставится и запускается в симуляторе (`npm run run:ios`); включение — вручную |

Сама панель во всех трёх браузерах — один и тот же content script, поэтому
проверка в Chromium покрывает и логику сравнения, и вёрстку. Неизвестной
остаётся ровно установка: она у каждого браузера своя.

## Как это устроено

Превью бинарных файлов GitHub рисует в отдельном фрейме на своём домене —
`viewscreen.githubusercontent.com`. Там же живут обе версии картинки и
переключатель режимов, поэтому расширение работает внутри этого фрейма и по его
правилам: своя радиокнопка в `.js-view-modes`, свой контейнер, свой ползунок.
Адреса картинок берутся из параметров `enc_url1` и `enc_url2` в адресе фрейма,
загружаются с `raw.githubusercontent.com` (он отдаёт
`access-control-allow-origin: *`, поэтому холст остаётся читаемым) и
сравниваются через [pixelmatch](https://github.com/mapbox/pixelmatch).

Отсюда три следствия:

- **Страницы github.com расширение не видит вовсе.** Права — только на
  `viewscreen.githubusercontent.com`, где нет ни ваших репозиториев, ни сессии.
- Фонового процесса нет — только content script и поток, который он собирает
  себе сам. Завести Worker со своего адреса внутри чужой страницы расширение не
  может, поэтому исходники читаются через `fetch` и склеиваются в blob; если это
  не вышло, сравнение считается в общем потоке. Поэтому манифест почти не
  отличается между тремя браузерами: Firefox добавляет свой идентификатор,
  Safari берёт сборку как есть.
- Разметку панели просмотра GitHub меняет без предупреждений. Поэтому в тестах
  есть проверка на живой странице — она и сломается первой, если формат уедет.

## Разработка

```bash
npm run build     # сборка всех трёх целей
npm run build:site   # отдельная страница в dist/site
npm test          # тесты в образе Playwright (нужен Docker)
npm run package   # архивы для релиза в dist/release
npm run screenshots  # снимки для README и витрин, с живого пул-реквеста
```

На каждый push и пул-реквест GitHub гоняет офлайн-тесты в том же образе
Playwright и проверяет сборку Firefox через `web-ext lint`. Живой тест вынесен
в отдельный запуск — раз в неделю и по кнопке: он ломается от чужих изменений,
а не от наших, и блокировать пул-реквест не должен.

`main` защищена: прямой push запрещён всем, включая владельца. Всё попадает
туда пул-реквестом с двумя зелёными проверками, история остаётся линейной —
только squash.

Релиз выпускает себя сам, по заголовкам коммитов. Они пишутся в формате
[conventional commits](https://www.conventionalcommits.org/) — `feat:`, `fix:`,
`docs:`, `refactor:`, `ci:`, `chore:` — и по-английски: они попадают в changelog
и в заметки к релизу, а читают их те же люди, для которых написан README. Тело
коммита — какое угодно.

Префиксы и что каждый делает:

| Префикс | Версия | Changelog |
| --- | --- | --- |
| `feat:` | minor | **Features** |
| `fix:` | patch | **Bug Fixes** |
| `perf:` | patch | **Performance** |
| `docs:` | patch | **Documentation** |
| `refactor:` | patch | **Refactors** |
| `chore:` `ci:` `build:` `test:` `style:` | patch | скрыт |
| любой из них с `!` | **major** | выделен |

Выбирать надо по тому, что изменение делает для того, кто расширением
пользуется, а не по тому, сколько сил ушло: правка в одну строку, чинящая
поведение, — это `fix:`, а большой рефакторинг, которого никто не заметит, —
`refactor:`. Префикс никто не проверяет: ошибиться можно молча, а к моменту
слияния версия и строка в changelog уже собраны из него.

Слияние здесь только squash, и заголовок пул-реквеста становится тем самым
единственным коммитом. То есть заголовок — не подпись, которую дописывают перед
слиянием, а заметка к релизу.

release-please читает их, считает следующую версию и держит открытым
пул-реквест с ней: версия поднята в `package.json` и манифесте, changelog
дописан. Слияние этого пул-реквеста создаёт тег и релиз, а тот же запуск
собирает архивы, прикладывает их и отправляет сборку в Chrome Web Store и на
addons.mozilla.org. Каждая витрина включается своей переменной репозитория,
поэтому форк не станет публиковать что-то от чужого имени — подробности в
[docs/PUBLISHING.md](docs/PUBLISHING.md).

Всё это обязано уместиться в один запуск: события, порождённые `GITHUB_TOKEN`,
чужие workflow не запускают, так что ждать появления тега здесь нечему.

То же правило стоит одного ручного шага. Релизный пул-реквест открывает
`GITHUB_TOKEN`, поэтому проверки на нём сами не начнутся, а `main` их требует.
Нажмите на нём **Close** и сразу **Reopen**: событие теперь от человека,
проверки идут, и дальше он сливается как любой другой.

Тесты — четыре уровня. `tests/parse.spec.js` проверяет разбор адресов, подмену
репозитория и поиск области различий, не трогая DOM. `tests/frame.spec.js`
загружает расширение в заглушку фрейма GitHub и проверяет, как оно уживается с
чужой разметкой: что в каждый момент виден ровно один режим, что панель не
меняет высоту документа, что содержимое не расползается по высокому фрейму.
Каждое из этого хоть раз ломалось и находилось глазами на скриншоте.
`tests/live.spec.js` поднимает настоящий Chromium с загруженным расширением,
открывает
[пул-реквест-полигон](https://github.com/Nemo-Illusionist/gh-pixel-diff/pull/1)
и убеждается, что режим встал в ряд к родным и посчитал разницу.
`tests/locales.spec.js` и `tests/popup.spec.js` в браузер не ходят вовсе:
первый проверяет, что каждая строка, которую просит код, есть во всех локалях,
второй — что разметка внутри переведённой строки разбирается узлами, а не
съедает половину фразы.

Полигон — открытый пул-реквест с одной изменённой картинкой в этом же
репозитории; он намеренно не сливается. Раньше тест ходил на чужой пул-реквест,
и тот перестал годиться, когда форк с исходной картинкой удалили.

Прогон идёт в контейнере, чтобы результат не зависел от того, что стоит на
машине.

Строки интерфейса лежат в `src/_locales`. Английский — запасной язык для всех
остальных; новый язык — это копия `en/messages.json` с переведёнными значениями,
у русского есть две дополнительные формы множественного числа, и нужную выбирает
`Intl.PluralRules`.
